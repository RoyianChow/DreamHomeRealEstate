## 1. Response envelope

Every endpoint answers with the same shape.

```jsonc
// success
{ "success": true, "data": { /* object or array */ } }

// failure
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",          // stable machine code
    "message": "Please correct the highlighted fields.",  // safe, shown to the user
    "fieldErrors": { "email": "Enter a valid email address" }  // optional
  }
}
```

`fieldErrors` keys are the JSON field names below. The forms map them straight
onto the matching input, so a server-side rule produces the same red message as
a browser-side one.

### Status codes

| Status | `code` | When |
| --- | --- | --- |
| 200 | – | Read or update succeeded |
| 201 | – | Insert succeeded |
| 400 | `VALIDATION_ERROR` | Input failed the shared schema |
| 404 | `NOT_FOUND` | No row for that key |
| 409 | `DUPLICATE` | Key or unique value already exists |
| 500 | `DATABASE_ERROR` / `SERVER_ERROR` | Anything else, with a generic message |

Never return credentials, raw SQL, or an Oracle stack trace. `handleUnexpected()`
in `lib/server/http.ts` already enforces this: unknown errors are logged on the
server and replaced with a generic sentence.

## 2. Endpoints

### Staff

| Method | Path | Body | Success |
| --- | --- | --- | --- |
| GET | `/api/staff` | – | 200, `Staff[]` |
| POST | `/api/staff` | `StaffHireInput` (the nine inputs) | 201, `Staff` |
| PATCH | `/api/staff/{staffNo}` | `StaffUpdateInput` | 200, `Staff` |

```ts
type Staff = {
  staffNo: string;   // generated by the database, never submitted
  firstName: string; lastName: string; position: string;
  branchNo: string;  // references DH_BRANCH
  dob: string;       // "yyyy-mm-dd"
  salary: number; telephone: string; mobile: string; email: string;
};

type StaffHireInput = Omit<Staff, "staffNo">;              // exactly nine fields
type StaffUpdateInput = Partial<Pick<Staff, "salary" | "telephone" | "email">>;
```

* `POST` calls `Staff_hire_sp`. The response **must** include the generated
  `staffNo` - the UI shows it in the success banner as proof of the insert.
* `PATCH` accepts salary, telephone and email only. Any other key is dropped by
  the schema before the data source is called.

### Branch

| Method | Path | Body | Success |
| --- | --- | --- | --- |
| GET | `/api/branches` | – | 200, `Branch[]` |
| GET | `/api/branches/{branchNo}/address` | – | 200, `BranchAddress` |
| POST | `/api/branches` | `BranchCreateInput` | 201, `Branch` |
| PATCH | `/api/branches/{branchNo}` | `BranchUpdateInput` | 200, `Branch` |

```ts
type Branch = { branchNo: string; street: string; city: string; postcode: string };
type BranchAddress = { branchNo: string; street: string; city: string };
type BranchCreateInput = Branch;
type BranchUpdateInput = Partial<Pick<Branch, "street" | "city" | "postcode">>;
```

* The address lookup is the required "enter a branch number, get street and
  city" feature. An unknown branch number is **404 with a message**, not an
  empty 200.
* `POST` calls `new_branch` against `DH_BRANCH`.
* `branchNo` travels in the URL for PATCH and is not part of the payload, so the
  primary key cannot be rewritten.

### Client

| Method | Path | Body | Success |
| --- | --- | --- | --- |
| GET | `/api/clients` | – | 200, `Client[]` |
| POST | `/api/clients` | `ClientCreateInput` | 201, `Client` |
| PATCH | `/api/clients/{clientNo}` | `ClientUpdateInput` | 200, `Client` |

```ts
type Client = {
  clientNo: string;               // locates the record, never updated
  firstName: string; lastName: string; telephone: string;
  preferredPropertyType: "House" | "Flat";
  maxRent: number;
};

type ClientCreateInput = Omit<Client, "clientNo">;
type ClientUpdateInput = Partial<Omit<Client, "clientNo">>;  // at least one field
```

* An update may carry one field or all five. An empty body is 400 with
  "Change at least one field before saving".

### Health

`GET /api/health` → 200, `{ dataSource: "oracle" | "mock", connected: boolean, detail: string, checkedAt: string }`.

Always 200, even when the database is down - a failed check is a normal answer
to this question. It drives the connection badge in the header.

## 4. Rules the server keeps

1. Validate with the shared schemas in `lib/validation.ts`; the server is the
   final authority even though the browser runs the same rules first.
2. Bind variables for every value - no string concatenation into SQL.
3. Update allowlists are the schemas themselves. `STAFFNO`, `BRANCHNO` and
   `CLIENTNO` are not in any update type, so they cannot be changed.
4. Commit only after the whole write succeeds; roll back on failure; release the
   connection in a `finally` block.
5. Node.js runtime on every route (`export const runtime = "nodejs"`), and the
   Oracle module is imported from server files only.

## 5. How Member 3 plugs Oracle in

1. Create `lib/server/oracle-data-source.ts` exporting an object that implements
   `DreamHomeDataSource` from `lib/server/contracts.ts`.
2. Throw `new DataError("NOT_FOUND" | "DUPLICATE" | "DATABASE_ERROR", message)`
   for expected failures; the route handlers map those to status codes.
3. In `lib/server/data-source.ts`, replace the placeholder `throw` with the
   import and return.
4. Set `DATA_SOURCE=oracle` in `.env.local`.

Nothing in `app/` or `components/` changes. The badge in the header flips from
amber "Mock data" to green "Oracle connected" and the pages carry on working.
